# PawBridge 현재 상태 확인 절차

이 문서는 저장소 루트의 AGENTS.md에서 현재 상태 판단 작업에 연결하는 상세 절차다.
경로는 AGENTS.md가 위치한 저장소 루트 기준이며, 서비스 하위 디렉터리에서도 같은 파일을 읽는다.

## A. 적용 조건과 확인 범위

현재 구현, 기술 사용 여부, 구성, 장애 원인 또는 운영 상태가 답변의 근거인 경우에 적용한다. 수정 여부와 관계없다. 일반 개념 설명, 사용자가 지정한 과거 버전 비교, 이미 확인한 사실을 같은 기준에서 다시 설명하는 경우에는 불필요한 최신 상태 조사를 추가하지 않는다.

사용자의 질문을 먼저 분류한다. 구분이 답변에 영향을 주고 현재 문맥으로 결정할 수 없으면 가능한 독립 조사를 진행하면서 필요한 대상만 물어본다. 코드를 바꾸려는 것이 아니라는 이유로 확인을 생략하지 않는다.

| 질문의 대상 | 우선 확인할 근거 | 함께 구분할 상태 |
| --- | --- | --- |
| 현재 개발 기준의 구현·아키텍처 | 사용자 지정 기준. 지정이 없으면 이 저장소의 기본 기준인 현재 원격 `dev`의 커밋 | 로컬 작업 폴더, 다른 브랜치, 배포본과의 차이. 기본 브랜치가 없으면 다른 브랜치로 임의 대체하지 않고 기준을 확인 |
| 특정 PR·브랜치·작업 중 변경 | 지정된 PR head/base, 브랜치와 실제 변경 내역. 로컬 검토라면 미커밋·미추적 변경도 범위에 따라 포함 | `dev`로 임의 대체하지 않음. 원격 PR과 로컬 변경의 차이 |
| 운영 또는 테스트 환경의 실제 동작·사용 여부 | 대상 환경의 실제 배포 버전, 적용 구성, 관련 상태·로그·메트릭 | 소스의 구현, 의도한 매니페스트, 실제 적용, 동작 검증을 구분 |
| 계획·합의·마이그레이션 경위 | 관련 Obsidian 정본과 사용자 합의 | 승인된 계획, 구현, 병합, 배포, 종료 또는 보류를 구분 |
| 지정된 과거 상태 | 지정된 커밋·태그·시점·기록 | 과거 사실을 현재 상태로 확대하지 않음 |
| 순수한 개념·가정 | 질문의 전제와 필요한 기술 근거 | 현재 PawBridge에서 사용 중이라는 주장으로 연결하면 해당 부분은 현재 상태 확인 대상 |

## B. 저장소·기준·작업 상태 식별

이 절은 코드나 저장소를 근거로 판단할 때 적용한다. 단순한 환경 상태 조회는 필요한 환경 근거만 확인한다. 예를 들어 파드 실행 여부만 묻는 질문에는 해당 환경의 상태 조회로 답하며, 소스나 배포 버전이 결론에 영향을 주지 않으면 Git 조사를 추가하지 않는다.

1. 실제 조사 경로의 Git 최상위 경로와 `origin`으로 저장소를 식별하고, 브랜치·HEAD·작업 트리 변경 여부를 확인한다. 필요할 때만 연결된 작업 트리와 비교한다. 인증정보가 포함될 수 있는 원격 URL은 그대로 출력하지 않는다.
2. 질문의 대상에 맞는 기준을 정한다. 원본 작업 트리는 `main` 브랜치나 최신 기준이라는 뜻이 아니다. 운영을 설명하면서 최신 `dev`를 운영 버전으로 대신하지 않는다.
3. 최신 원격 상태가 필요하면 해당 원격 브랜치의 SHA를 확인한다. 로컬 `origin/dev` 이름만 보거나 최근 파일 수정 시각만 보고 최신이라고 표현하지 않는다. 원격 조회 또는 갱신의 성공 시점과 확인한 SHA를 작업 내 근거로 유지한다. 브랜치가 조회 후 이동할 수 있으므로 확인한 SHA와 실제 읽는 객체를 일치시킨다. 객체 확보 중 다른 SHA가 확인됐다면 새로 확인한 기준으로 명시한다. 원격 확인과 객체 확보가 필요할 때는 기존 규칙 안에서 수행하며, 명령은 현재 저장소·리모트·브랜치에 맞춘다.
4. 로컬 HEAD가 기준과 다르면 질문에 필요한 차이와 관련 경로부터 확인한다. 전체 차이를 매번 나열하지 않는다. PR 검토에는 확인한 base/head와 그 merge-base를 기준으로 한 변경 내역 또는 해당 PR의 실제 diff를 사용한다. base와 head의 단순 트리 차이를 PR 변경으로 대신하지 않는다. 미커밋 변경을 포함했는지 명시한다.
5. 커밋·브랜치·PR의 버전 관리된 기준 코드는 확인한 SHA를 고정해 읽는다. 필요한 객체가 있으면 `git show <SHA>:<경로>`로 읽거나 격리된 임시 디렉터리에 내보낸다. 객체가 없으면 필요한 범위만 확보한다. 로컬 작업 중 변경이 검토 대상이면 HEAD 기준 코드와 스테이징·미스테이징 변경, 관련 미추적 파일을 함께 읽는다. 커밋만 내보낸 결과를 로컬 변경까지 검토한 것으로 표현하지 않는다. 단순 조회를 위해 사용자 브랜치를 전환하거나 기존 변경을 stash·reset·삭제하지 않는다. 분리 작업 트리 생성 등 승인 대상 작업의 권한을 이 절차에서 추정하지 않는다.
6. 여러 저장소를 연결해 판단할 때는 각각의 기준을 확인한다. 연동 동작을 판단할 때는 질문 대상의 빌드·배포·설정이 실제로 연결하는 커밋·이미지·패키지 버전도 확인한다. 각 저장소의 최신 코드가 확인됐다는 이유로 서로 그 버전끼리 연결되어 있다고 가정하지 않는다. 한 저장소의 최신 확인을 다른 저장소나 연동 환경의 최신 확인으로 확대하지 않는다. 현재 저장소 지침을 다른 저장소에 자동 적용하지 않는다.

## C. 근거의 의미와 문서 확인

1. 코드 파일이 있다는 사실은 그 커밋에 구현 또는 설정이 존재한다는 근거다. 서비스가 운영 중이거나 설정이 적용됐다는 근거와 구분한다. 샘플·폐기된 경로·비활성 프로필·등록되지 않은 차트·이전 마이그레이션 자산의 가능성을 필요한 실행 경로에서 확인한다.
2. 파일이나 참조를 찾지 못했다는 사실만으로 기능이 제거됐거나 사용하지 않는다고 단정하지 않는다. 조사한 커밋과 검색 범위를 밝히고, 주장을 위해 필요한 호출·설정·의존성 또는 배포 근거를 확인한다.
3. 관련 계획·이관·종료 결정에 의존할 때 Obsidian 정본을 확인한다. 날짜·파일명·수정 시각만으로 최신 승인본을 결정하지 않는다. 후속 결정과 완료·보류 상태를 확인하고 실제 코드·배포 상태와 구분한다.
4. 기억과 과거 채팅은 관련 경로·결정을 찾는 단서로 사용한다. 코드·문서·사용자 설명이 충돌하면 각 근거의 대상과 시점을 비교한다. 과거 코드와 같은 시기의 기억이 일치한다는 이유로 현재 사실로 확정하지 않는다. 사용자 설명과 아직 검증하지 않은 사실을 구분하고 충돌이 해소되지 않으면 드러낸다.
5. 실제 사용·배포·장애 원인처럼 운영에 관한 주장은 그 주장을 뒷받침하는 환경별 근거까지 확인한다. 코드만 조사한 경우에는 구현 기준의 판단으로 한정한다. 배포 버전만 확인한 경우에도 기능의 실제 성공까지 검증했다고 표현하지 않는다.

## D. 확인 실패와 재확인

1. 원격·배포 환경·정본 문서에 접근하지 못하면 확인한 경로·커밋·환경과 실패한 확인을 구분해 보고한다. 오래된 로컬 자료만 있으면 해당 자료 기준이라고 명시한다. 확인하지 않은 최신 상태에만 의존하는 결론은 보류하고, 개념 설명·지정 버전 분석 등 독립적으로 가능한 작업은 이어간다.
2. 조회 실패만으로 사용자에게 재부팅·로그인·설치·권한 변경을 요구하지 않는다. 원인에 맞는 범위 내 대안과 기존 승인 여부를 먼저 확인한다. 필요한 사용자 조치가 있으면 실패 근거와 필요한 최소 조치를 설명한다.
3. 동일한 작업에서 확인한 불변 커밋을 계속 읽는 경우에는 매 답변마다 원격 조회를 반복하지 않는다. 대상 저장소·기준·환경이 바뀌거나, 병합·배포·동시 작업 등 변경 근거가 생기거나, 작업을 오래 중단했다가 현재 상태의 판단을 재개하거나, 사용자가 다시 현재·최신 상태를 확인해 달라고 하면 필요한 범위만 새로 확인한다. 동일한 커밋에 대한 과거 확인은 유지할 수 있지만, 그 커밋이 여전히 원격 최신이라는 주장은 별도로 확인해야 한다. 실시간 상태는 오래된 확인을 현재 상태로 재사용하지 않는다.
4. 간단한 상태 확인은 한 번의 필요한 명령으로 묶어 수행한다. 성공 후 중복 확인하지 않는다. 실패 시 실질적으로 다른 대안은 최대 한 번 시도한다. 복합 조사도 질문에 필요한 범위에서 단계적으로 진행하고, 모든 저장소·클러스터를 습관적으로 조사하지 않는다.
5. 근거를 확보하기 위한 네트워크·장시간 작업은 기존 알림 규칙을 따른다. 브랜치 변경·커밋·푸시·병합·배포·파괴적 작업·비밀값 변경은 기존 승인 규칙을 그대로 따른다. 읽기 전용 조사라는 명목으로 운영 리소스를 변경하지 않는다.

## E. 보고와 문서 유지

1. 현재 상태가 결론에 영향을 주면 확인한 대상과 기준을 간결하게 함께 제시한다. 예: `원격 dev의 <SHA>에서 구현 확인. 운영 배포 여부는 미확인.` 모든 일반 설명에 전체 Git 상태표를 붙이지 않는다.
2. 실제 코드·테스트·배포 근거와 추정·제안·미확인을 구분한다. 검증 범위 밖의 기능이나 환경으로 결론을 확대하지 않는다.
3. AGENTS.md에는 핵심 불변 원칙과 이 문서의 적용 조건을 두고, 절차의 상세 내용은 이 문서를 정본으로 둔다. 링크와 세부 내용이 충돌하지 않도록 함께 검토한다. 연결 문서가 누락되면 그 사실을 보고하고 AGENTS.md 핵심 규칙과 현재 사용자 지시에 따라 가능한 범위에서 진행한다.
4. 이 경로는 일반 Markdown 파일의 위치다. Codex가 `.agents/rules` 아래 모든 파일을 자동으로 읽는다고 가정하지 않는다. AGENTS.md의 명시적 참조와 작업 중 읽기로 적용한다. 지침 파일 변경 후 같은 세션에 자동 반영됐다고 가정하지 않고 필요한 지침을 다시 읽는다. 실제 적용을 검증할 때는 대상 루트·서비스 경로의 유효 AGENTS 지침과 연결 문서가 읽혔는지 확인한다. AGENTS.override.md나 설정된 로딩 용량에 의해 이 규칙이 제외되지 않았는지도 해당 환경에서 확인한다. 지침 로딩 검증을 이유로 사용자 앱 재시작이나 설정 변경을 자동 요구하지 않는다.
5. 이 절차는 판단 누락을 줄이기 위한 지침이다. 자동 검사나 CI에 의한 강제 차단 또는 재발 방지의 완전한 보장을 제공한다고 표현하지 않는다.
